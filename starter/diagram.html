03 / RELATIONSHIP SPECIMEN · TERRAFORM / GCS

Shared code. Separate state.

Can two deployments share module code while keeping their state separate? Yes. Here, two independently run root configurations call the same module source and use distinct backend state objects.

Illustrative assumptions. Both roots use the same repository revision and the default workspace. One pre-existing example bucket, kc-state-example, uses distinct prefixes dev and prod, producing gs://kc-state-example/dev/default.tfstate and gs://kc-state-example/prod/default.tfstate. These names do not identify deployed infrastructure.

Limits. Distinct objects separate state storage, but do not establish IAM isolation or prevent both roots from targeting the same real resource. Assume distinct resource identities and no cross-state reads for this example. State records resource mappings, not application data. A local source edit can affect both roots on their next run; sharing source does not deploy either root automatically.

Inspecting 01 · Module source

MODULE

01 · Module source

This excerpt shows the resource shape only. Provider configuration, inputs, networking, and resource settings are omitted. A child module does not receive an independent backend merely because it has its own folder.

modules/cloud-sql-ha/main.tf
resource "google_sql_database_instance" "primary" {
  name             = var.instance_name
  database_version = "POSTGRES_15"
  # Required settings and other inputs omitted.
}
ROOT

02 · Dev root

Run Terraform independently from this root. The same source path is resolved relative to each root; use distinct inputs and resource identities.

envs/dev/cloud-sql/main.tf
module "database" {
  source        = "../../../modules/cloud-sql-ha"
  instance_name = "example-dev-db"
  # Other module inputs omitted.
}
STATE

03 · Dev ledger

With the default workspace, this backend stores state at gs://kc-state-example/dev/default.tfstate. The bucket must already exist. Authentication and IAM are configured separately.

envs/dev/cloud-sql/backend.tf
terraform {
  backend "gcs" {
    bucket = "kc-state-example"
    prefix = "dev"
  }
}
ROOT

04 · Prod root

This second root calls the same blueprint. Separate state is not a guarantee of independent permissions, resource targets, or failure impact.

envs/prod/cloud-sql/main.tf
module "database" {
  source        = "../../../modules/cloud-sql-ha"
  instance_name = "example-prod-db"
  # Other module inputs omitted.
}
STATE

05 · Prod ledger

With the default workspace, this backend stores state at gs://kc-state-example/prod/default.tfstate. GCS supports state locking; locking does not create an environment-wide transaction.

envs/prod/cloud-sql/backend.tf
terraform {
  backend "gcs" {
    bucket = "kc-state-example"
    prefix = "prod"
  }
}
