# Explaining relationships with Kinetic Serif

This is reusable authoring guidance. The [module/root/state specimen](../starter/diagram.html) demonstrates one topology. Its Terraform/GCS assumptions are recorded in [architecture-spec.md](architecture-spec.md); they are not universal design rules. Sequence, flowchart, and state diagrams below are selection advice, not implemented components in this pilot.

## Start with a brief

Write down the reader, the question they need answered, the scope, the evidence or assumptions, and a one-sentence takeaway. Reuse existing context instead of requiring a questionnaire. If the answer fits a sentence, start there. Add a visual when it makes a relationship easier to trace or compare.

## Choose a representation

| Reader needs to know | Start with | Check before drawing |
| --- | --- | --- |
| What something means or why it matters | Prose and a concrete example | Would a graphic add anything? |
| How attributes or options compare | Table | Can readers compare the same attribute across rows? |
| What depends on or connects to what | Topology | Does every edge name its relationship and direction? |
| Who sends what, in what order | Sequence | Are actors, message order, and any waits explicit? |
| Which condition changes the path | Flowchart | Are branches labeled with conditions and outcomes? |
| Which states and transitions are possible | State diagram | Are nodes states, and transitions labeled with triggers or guards? |

Containment can show membership within a topology, but a folder, environment, administrative scope, and security boundary are different claims. Label the kind of boundary. A procedure is often clearer as numbered steps. Split a figure when the reader's question or abstraction changes, or the important path becomes hard to trace; no fixed node count is a cognitive law.

## The demonstrated figure contract

1. **Frame the answer.** A visible question, informative heading, scope line, and takeaway caption precede optional details. Name assumptions and omissions near the figure.
2. **Name each node.** Give it a type, readable name, stable identifier, and a concise responsibility in adjacent text. In the specimen, module means reusable source, root means an entry configuration used for execution, and state means persisted resource mapping. A root configuration is not a deployed service. Use a neutral treatment for actors or systems outside these roles. Classify by responsibility: an API schema is source/definition, a running API service is execution, a database is persisted state, and an external customer is neutral. A different subject may need a separately named role; do not assign a familiar color merely because a box needs emphasis.
3. **Name each edge.** Use subject → object, with a direct verb phrase. “Root → module: calls source” is a dependency; “root's Terraform run → state: reads/writes state” is an association aggregating access in both directions. The arrow identifies the subject and target; it is not packet direction, a complete data flow, or a timeline. Do not silently mix meanings.
4. **Name each boundary.** Dashed outlines in this specimen group environment configuration and its state association. They do not assert network or IAM enforcement, nor physical storage containment. Other boundary meanings require a new label and legend.
5. **Separate role from interaction.** Indigo/source, moss/root, and sienna/state retain their domain meanings. A check mark, neutral outline, and `aria-pressed` communicate inspector selection. A separate focus outline identifies keyboard focus. Generic primary actions use action tokens; green on a button does not label a root node. Warnings need explicit text, not a reused role color.
6. **Keep geometry readable.** Route orthogonal connectors with rounded elbows, attach them perpendicularly to nodes, separate routes, and place labels off their strokes with opaque masks. Use a stable reading order. Passive nodes have role borders; tactile shadows belong to controls and established card chrome.
7. **Provide an equivalent route.** Keep a visible relationship table or readable explanation with every essential edge, node type, scope, and caveat. Give the SVG a unique title and description. Do not rely on hover or the SVG description alone.

## Copy the pattern

Copy the marked `BEGIN module-state specimen` section from [starter/diagram.html](../starter/diagram.html), with the shared CSS and JS. The standalone page is the canonical specimen source. Its mirrored chapter in `index.html` is generated by `python3 sync_reference.py`.

The static figure uses `.diagram-figure`, `.diagram-scroll`, and `.relationship-diagram`. The 880 × 480 viewBox renders at a minimum width of 880 CSS pixels: prose labels are 15px, technical identifiers/type labels 13px, and Fraunces node names 20px. The SVG can grow on wider layouts. On narrow layouts it scrolls inside a keyboard-focusable labeled region; surrounding prose and the table reflow. Do not shrink all text to fit a phone. When duplicating a figure, change all SVG title/description/marker IDs, HTML detail IDs, and corresponding ARIA references to remain unique.

The optional native `<details>` inspector contains normal buttons grouped with `role="group"`. Each button's `data-node` matches one article's `data-detail`; `aria-controls` references its article ID. Runtime enhancement exposes the controls, selects the first node, sets exactly one `aria-pressed="true"`, hides other articles, and announces the selected name via a polite status. Tab reaches each button, Enter or Space selects, and focus stays on the button; Tab continues into visible code/copy controls. These are buttons, not tabs: arrow-key navigation is not promised. The check mark and `.selected` outline are independent of role colors.

Without JavaScript, selection controls stay hidden and all five code excerpts remain available inside native details. The overview, table, assumptions, and caption remain visible. Print keeps that same core lesson and omits the optional inspector. No animation is needed.

## Review meaning separately from appearance

First give only the page or its readable text to a fresh reader. Ask: What is shared? What stays separate? Explain every arrow. What does each dashed box claim? Which objects are actually deployed, and what was omitted? What conditions could invalidate the example? Then give an author only the distributed guide and specimen and ask them to reproduce the pattern. Record ambiguity and revise it before visual polish.

Separately inspect the rendered page: both themes, keyboard controls and focus/selection, normal text at least 4.5:1 and meaningful graphics at least 3:1 against adjacent colors, narrow widths/zoom, no JavaScript, and print. Test loaded fonts as well as fallbacks when available. Automated checks and an AI reader diagnostic do not replace a human usability or screen-reader study.

The local [research report](../docs/research/2026-10-26-information-design-review.md) records the source register and limitations behind these choices. These conventions adapt C4 notation and information-design heuristics; they do not adopt a complete C4 model or claim one visual form always outperforms a table.
